ℹ️
Scope of this guide: This covers Marketing Intelligence (MI) — the measurement and analytics layer. It is distinct from Marketing Cloud Intelligence (formerly Datorama) and from Marketing Cloud Engagement (MCE) reporting.

What is Marketing Intelligence?

Marketing Intelligence is Salesforce's answer to fragmented marketing measurement. It sits on top of Data Cloud and provides a unified measurement layer that connects all your marketing signals — paid media APIs, owned channels (email, SMS, push), Salesforce CRM data — into a consistent, harmonized model.

The result is a platform where you can run multi-touch attribution, marketing mix modeling, budget optimization, and AI-driven recommendations from a single source of truth.

Unified Data Model
Data Foundation › Unified Data Model

Unified Data Model

The Unified Data Model is the semantic layer that sits between raw marketing data (DLOs) and the analytics surfaces MI exposes. It ensures that a "Campaign" from Google Ads means the same thing as a "Campaign" from Meta Ads.

Semantic Data Model (SDM)

The SDM is the core schema that MI deploys. It contains pre-built Data Model Objects (DMOs) for the most common marketing dimensions:

  • Campaigns — top-level marketing initiatives
  • Ad Sets / Line Items — audience or placement groupings
  • Creatives / Ads — individual ad units (format, size, variant)
  • Channels — paid search, social, display, email, SMS, etc.
  • Conversion Events — form fills, leads, purchases, opportunity stage changes
  • Engagement Signals — clicks, opens, impressions (underpins MTA)
ℹ️
C360 and MI: The Customer 360 Data Model (C360 SDM) is only deployed via MI. If a customer does not have MI, the C360 SDM is not available. MCE, MCAE, and MCN are backwards-compatible with the SDM by design — they populate the SDM automatically via Data Cloud.

Native Salesforce Data Path

When data already lands in Salesforce (CRM leads, opportunities, MCE sends), MI can reference it directly:

  • Native SF data → recognized by the SDM — this is the simplest integration path
  • MCE email sends → flow automatically via Data Cloud into the C360 SDM and MI DMOs
  • No duplicate ingestion cost for data already in Salesforce
💡

Overview Data Pipelines
Data Foundation › Data Pipelines

Data Pipelines

Data pipelines are the connectors that pull raw marketing data from external platforms into MI's data layer. All ingestion in MI is batch — there is no real-time data ingestion.

ℹ️
Typical customer footprint: ~15 data pipelines on average. This can multiply significantly for multi-BU or multi-brand organisations, where each BU may have its own pipeline set.

Ingestion Categories

APIs — Paid Media Connectors

Direct API connections to platforms such as Google Ads, Meta, LinkedIn, TikTok, Pinterest, and many more. These pull raw campaign, ad set, creative, impression, click, and spend data.

  • Data is ingested as raw streams — not yet mapped to the SDM
  • Multiple streams per platform (e.g., Google Ads has campaign, ad group, keyword, search term streams)
  • Snapshots of up to 365 days of historical data can be ingested per pipeline
⚠️
The 365-day snapshot limit is a platform constraint that is not clearly communicated in the UI. For multi-year backfills, customers must run two separate snapshots: e.g., 1 Jan–31 Dec 2024, then 1 Jan–31 Dec 2025.
Native DLO (Total Connect)

Total Connect is MI's native connector framework for certain certified data sources. It handles schema mapping more automatically than raw API ingestion.

  • Used for supported paid media channels where MI has a native connector
  • Does not apply to external email service providers — those go through Data Cloud
  • Preferred path for speed and reliability
Native Salesforce Data

Data already in the Salesforce ecosystem — CRM objects, MCE send/click/open events, MCAE activities — can be referenced directly by the SDM.

  • MCE data flows automatically via Data Cloud into the SDM
  • No re-ingestion required for data that already lives in Salesforce
  • Work has been done in 2025 to ensure the SDM correctly understands native SF data
File-Based Ingestion

For sources without a direct API connector (e.g., TV ratings, offline spend, custom data), flat files can be ingested via Total Connect Sources.

  • Useful for TV/OOH spend data in MMM configuration
  • Can also support custom external factors for the MMM model

Restatements & Sliding Windows

Many ad platforms retroactively revise performance data (view-through conversions, deduplication, fraud adjustments). MI handles this through sliding windows.

Unified Data Model Data Harmonization
Data Foundation › Data Harmonization

Data Harmonization

Harmonization is the process of standardising raw, inconsistent marketing data into clean, reportable dimensions. Marketing Intelligence provides native harmonization through Patterns and the SDM — no SQL required for most use cases.

What is a Pattern?

A Pattern is a rule that extracts a structured dimension from a raw string field — typically the campaign name, ad set name, or UTM parameter. Because marketers encode metadata in naming conventions (e.g., UK_Q4_ProspectingF25-34_VideoV1), Patterns parse these strings into usable dimensions.

ℹ️
Once a Pattern is created, it applies retroactively — pre-existing fields can immediately be selected in reports using the new dimension. No re-ingestion needed.

Common Use Cases

📣

Campaign Dimension

Extract campaign theme, objective, or region from campaign name strings.

🎯

Audience (Ad Set)

Parse gender, age bracket, interest, or audience type. E.g. Female_25-34 → Gender: Female, Age: 25–34.

🎨

Creative Attributes

Extract format (video/static), size (1080x1080), or variant (A/B/C) from ad names.

🌍

Geography

Parse country, region, or market code. E.g. Country Q4 → Country: extracted, Quarter: Q4.

SE Discovery Tip

Always ask the customer about their naming conventions and UTM taxonomy during discovery. If the metadata isn't captured in the name or UTMs, Patterns can't create it. As the saying goes: "It's not magic — you have to capture the data."

Custom Dimensions

Beyond Patterns, customers can create custom dimensions outside the standard SDM using the custom SDM extension. This is for dimensions that don't fit any of the standard pattern extractions — for example, a proprietary campaign classification system.

Data Enrichments

Enrichments allow customers to augment their harmonized marketing data with additional classification data via file-based lookups. Think of it as a VLOOKUP applied to your MI data — matching a code or key in one column to a label or category in another.

Key Characteristics

  • Unmetered — no flex credit consumption
  • File-based: a two-column lookup (key → value)
  • Applied line by line across the data
  • Everything in MI can be explored via Data Explorer
  • All use cases can be validated independently through Data Explorer

When to Use Enrichments vs. Data Transforms

ScenarioRecommended approach
Simple code-to-label mapping (e.g., "001" → "EMEA")Enrichment
Cleansing / grouping raw valuesEnrichment (good use case)
Multi-step logic, complex transformationsData Transform (better suited)
Output needed outside MI (e.g., for Segmentation in Data Cloud)Data Transform
💡
Multi-step enrichment logic is better handled with Data Transforms, especially if the enriched data needs to flow outside MI for use in segmentation or other Data Cloud workloads.

Common Enrichment Scenarios

  • Mapping campaign IDs to business unit labels
  • Translating platform-specific audience codes to standardised audience segments
  • Grouping raw creative format values (e.g., "15s_video", "30s_video", "6s_bumper" → "Video")
  • Mapping UTM source values to channel taxonomy
SE Guidance

Enrichments are a quick win for customers with messy lookup tables — especially those migrating from manual Excel-based reporting. The key qualification question: does the customer have a stable lookup table (e.g., cost centre codes), or do they need computed logic? Stable lookup → Enrichment. Logic → Data Transform.

Anchor Campaigns

When MI retrieves all campaigns from connected platforms, the raw list can be enormous — hundreds or thousands of line items across platforms, naming variations, and time periods. Anchor Campaigns let customers group this raw campaign data into meaningful marketing initiatives that reflect actual business goals.

The Core Concept

Think of an Anchor Campaign as a smart filter — a logical grouping rule that says "pull together everything that belongs to this initiative, regardless of platform or naming."

ℹ️
An Anchor Campaign is not a campaign object in the ad platform — it's a MI-layer construct that aggregates matching campaigns across channels into a single measurable entity.

How it Works

  1. Define a filter rule: e.g., Campaign Name contains "BrandAwareness_Q4"
  2. MI pulls in all matching campaigns across all connected channels and sources
  3. You can add multiple filter conditions (AND/OR logic) for more precise grouping
  4. All matching data rolls up into the Anchor Campaign for unified reporting

Example: Multi-Channel Brand Campaign

PlatformCampaign NameMatched?

MetaBrandAwareness_Q4_Prospecting_UK✅ Yes
LinkedInBrandAwareness_Q4_B2B_UK✅ Yes
DisplayRetargetingQ4_Display❌ No — different prefix

Multi-Filter Anchor Campaigns

You can take Anchor Campaigns further by combining multiple filter conditions:

  • Campaign name contains "BrandAwareness_Q4" AND Channel = "Paid Social"
  • Campaign name contains "Summer" OR Campaign name contains "July"
  • Market = "UK" AND Objective contains "Prospecting"
SE Discovery Question

Ask customers: "When you think about a campaign, do you think about individual platform line items, or do you think about the broader initiative across channels?" The answer usually reveals whether Anchor Campaigns will be a key feature for them. Most enterprise marketers think in initiatives — Anchor Campaigns bridge that gap.

Anchor Campaigns & Attribution

Anchor Campaigns feed directly into the measurement layer. Once defined, they become the unit of measurement for:

  • Cross-channel performance reporting
  • MTA conversion attribution at the campaign level
  • MMM contribution analysis by initiative
  • Goal tracking and progress measurement

Attribution Methods in MI

Single-Channel Performance

Reporting on each channel in isolation. Useful as a baseline but doesn't account for cross-channel interactions. MI supports this natively, and is often where customers start their journey.

Cross-Channel Performance

MI's strength — reporting at the media and marketing dimension level across channels simultaneously. The default model is last-touch unless de-duplication rules are configured. This is an extension of single-channel with the channels combined in a unified view.

A/B & Incrementality Testing

Showing an ad to a group vs. a holdout group to measure true causal impact. Expensive to run consistently and operationally complex — the whole business needs to agree on the holdout strategy.

  • Pairs well with segment-based targeting and creative A/B tests
  • Ties to audience suppression in paid platforms
⚠️
MI does not have a native experimentation module today. This is a known gap — customers need to manage holdouts externally.
Multi-Touch Attribution (MTA)

MTA credits individual touchpoints along the customer journey proportionally. This is MI's most sophisticated attribution capability.

Prerequisites for MTA

  • Timestamp on every touchpoint event
  • User ID — a consistent identifier across sessions (not GCLID alone)
  • Channel tagging on every touchpoint
  • Campaign tagging (UTMs, click IDs, etc.)
🔴
GCLID (Google Click ID) alone does not work for MTA. MI requires a resolvable user identity, not just a click ID. The customer must be able to identify the same person across paid ads, owned channels, and CRM.

MTA Limitations & Design Decisions

  • MTA operates on clicks only — not impressions
  • Each MTA configuration supports one conversion event
  • Customers can create multiple MTA configs for multiple conversion events
  • Conversion doesn't have to be end-of-funnel (e.g., add to cart, form fill, account open, loyalty redemption)
  • Opportunity status changes are not natively retained — only closed. For mid-funnel stages (e.g., Stage 4 → 5), a data transformation to create an event is required

Engagement Signals

Engagement Signals are the foundational tracking events that underpin MTA. They record individual email clicks, ad clicks, and other interactions at the user level. Key points:

  • A conversion metric must have an associated Engagement Signal
  • Engagement Signals is a concept shared across Sales Cloud, B2B Marketing (MCAE), and other Salesforce products — it's a foundational feature with broad applicability
  • Tracks individual email clicks, ad interactions, etc.

MTA Output Storage

ℹ️
MTA output is stored in the SDM. The inputs come from Data Cloud (D360) — not stored in the SDM. This is an important architecture distinction for data governance conversations.
Marketing Mix Modeling (MMM)

See the dedicated MMM page for full details. MMM complements MTA — when used together, the two models should improve each other's accuracy.

Identity Resolution — The Hard Part

The most common customer challenge in MTA is identity resolution — matching the same individual across paid advertising, web sessions, owned channels, and CRM.

Identity scenarioNotes
Salesforce-native data (CRM leads, MCE email)Easiest — Salesforce holds the identity, SDK can join it
Web / paid ads (cookies, click IDs)Requires the user to have identified themselves at some point. SDK preserves historic identity data to enable the join.
GCLID aloneNot sufficient — does not resolve to a unified identity
SE Framing

Identity resolution is fundamentally a customer data problem, not a MI problem. Salesforce (via the SDK) keeps historic identity data to enable the join — but only if the customer identified themselves at some point. The question to ask: "Can you tell me how you currently identify George across a paid ad click and a sales call?" Their answer reveals the complexity of the MTA deployment.

Marketing Mix Modeling

Marketing Mix Modeling (MMM) is a statistical approach that measures how each marketing channel contributes to revenue (or any conversion KPI) across the entire media mix — paid and owned. Unlike MTA, it works at an aggregate level using historical data, not individual user paths.

ℹ️
Look for Meridian as a tab within the Planning Center.

How MMM Works

  1. Load 2+ years of sales/conversion data
  2. Overlay media spend and impression data
  3. Run a regression analysis to find correlations between media activity and conversion variances
  4. Model derives baseline (what you'd achieve without any media) and media contribution (the uplift from each channel)
  5. Use outputs for scenario planning, what-if analysis, and budget optimization

Google Meridian — The Model

MI uses Google Meridian, an open-source MMM model, as the underlying statistical engine.

ℹ️
The model itself is open source — anyone can run it. Salesforce's value is not the model — it's what we do with the model. Meridian connected to MTA, Budget Optimization Agent, Scenario Planning, and the broader MI measurement layer is the differentiator.

MMM Configuration Steps

1. Marketing Data Sources

Select which data sources feed the model:

  • API Sources — from MI pipelines (MI must be set up with pipelines first)
  • Owned Media Data Sources — anything native to Salesforce (email opens, SMS, WhatsApp)
  • Total Connect Sources — e.g., TV ratings, offline spend
⚠️
MI pipelines must be configured before you can select API sources in MMM. You cannot run MMM on a bare org with no data pipelines.
2. Data Health & Confidence Score

After connecting sources, MI provides a data health check with:

  • A confidence score indicating model reliability given available data
  • Specific suggestions for improving data coverage and quality
3. KPI Configuration

Select the conversion KPI the model will optimize for:

  • Choose a DMO (e.g., Revenue Event) and the specific revenue field
  • Not every model runs off revenue — it is conversion-driven
  • Align KPI to the customer's actual business goal (e.g., leads, sales, app installs)
4. External Factors

Inject contextual factors that explain variance in performance unrelated to media:

  • Seasonality / holiday calendars
  • Google Search Query Volume
  • Competitor activity
  • Macroeconomic trends
  • Weather
  • Custom factors — any data the customer has in Data Cloud (e.g., additional economic indicators)
ℹ️
Custom external factors require the data to already be in Data Cloud (D360). Help customers plan for this during discovery.
5. MTA Integration (Optional)

If the customer also has MTA configured, the MTA model can be added here to improve MMM accuracy. When MTA and MMM are used together, they should mutually reinforce each other's output.

Measuring Goals

Goals in Marketing Intelligence allow marketers to define measurable objectives and track progress against them in a structured, dashboard-ready way. Goals bridge the gap between raw performance data and business outcomes.

The Goal Framework

Goals are structured around MI's measurement framework:

  1. Objectives — the high-level business intent (e.g., increase qualified leads in EMEA by 20%)
  2. Metrics — the quantifiable measures that track progress (e.g., MQL count, cost per lead, lead-to-opportunity conversion rate)
  3. Data Sources — the connected pipelines and CRM data that feed the metric
  4. Methods — the attribution approach used to interpret the metric (single-channel, cross-channel, MTA)

Conversion Events as Goals

Any conversion event configured in MI can be used as a goal metric:

  • Form fills
  • Leads / MQLs
  • Opportunities (created, or stage-based)
  • Revenue / purchases
  • Add to cart
  • Account opens
  • Loyalty redemptions
  • App installs
  • Email sign-ups
💡
Goals don't have to be end-of-funnel. Mid-funnel goals (e.g., "increase engagement with our awareness content") are valid and often more actionable for optimisation conversations.

Connecting Goals to Attribution

Goals defined in MI connect directly to:

  • MTA models — via Engagement Signals (each conversion event needs an associated engagement signal)
  • MMM — via the KPI configuration (the goal metric becomes the KPI the model optimises toward)
  • Dashboards — goals surface as performance indicators and progress trackers
  • Budget Optimization Agent — budget recommendations are made in service of the defined goal
SE Discovery

Kick off measurement conversations by asking: "What is ROI to you?" Different stakeholders will give different answers — digital marketing teams often say CPL or ROAS; CMOs often say revenue or pipeline contribution. Surfacing this misalignment early is a valuable discovery output and often opens the door for a broader MI conversation.

Budget Reallocation & Scenario Planning

One of MI's most compelling differentiators is connecting measurement insights directly to budget decisions. The Planning Center is where MMM outputs drive scenario planning and the Budget Optimization Agent surfaces actionable reallocation recommendations.

The Planning Center

The Planning Center is the MI interface for budget planning and optimization. After MMM runs, its outputs flow directly into the Planning Center:

  • View the Meridian MMM model output (accessible as the Meridian tab)
  • Run what-if scenario analysis — e.g., "what happens if we cut Meta by 20%?"
  • Simulate turning off individual channels to test their contribution
  • Compare budget scenarios against forecast performance

What-If Scenarios

The MMM model supports interactive scenario planning:

  • Remove or reduce a channel entirely (e.g., pause TV spend)
  • Reallocate from low-ROI to high-ROI channels
  • Model the impact of budget increases ahead of peak seasons
  • Understand diminishing returns curves per channel

Budget Optimization Agent

The Budget Optimization Agent is an Agentforce-powered AI agent that sits on top of MMM outputs and provides natural language budget recommendations. Rather than having a media strategist manually interpret model outputs, the agent surfaces the recommendation directly:

  • "Based on this quarter's model, reallocate 15% from Display to Paid Search to maximise lead volume"
  • Recommendations are grounded in the MMM model's channel contribution and ROI calculations
  • The agent can answer follow-up questions about the rationale
ℹ️
This is what differentiates MI from "just having Meridian." The model is open source — anyone can run it. What Salesforce provides is the downstream workflow: model → planning → agent recommendation → activation. That closed loop is the differentiator.
Competitive Positioning

When a prospect says "we already use MMM via a consultancy," the right response is: "Great — but how long does it take to go from model run to budget decision? With MI, that path is automated, connected, and visible to the whole team in Salesforce." The speed and integration into the planning workflow is the win, not the model itself.

Identity Resolution & the SDK

Identity resolution — matching the same real-world individual across different data sources and sessions — is foundational to MTA and any user-level measurement in MI.

Why Identity Matters

MTA requires a User ID at the touchpoint level to attribute a conversion back to the marketing journey that drove it. The challenge: the same person may appear as:

  • A cookie ID on your website
  • A GCLID (Google Click ID) from a paid search click
  • An email address in your CRM
  • A hashed email in a Meta audience
  • An anonymous user ID in a mobile app

Linking these to a single Unified Individual is identity resolution.

The SDK's Role

The Salesforce SDK (embedded in customer web and mobile properties) maintains historic identity data to enable the cross-session, cross-channel join:

  • Stores linkage between anonymous IDs and known IDs when a user identifies themselves
  • Enables retrospective resolution — if someone clicks an ad anonymously and later fills in a form, the SDK can join those two events
  • Requires the user to have identified themselves at some point — unknown-to-unknown resolution is not possible
🔴
GCLID alone does not work for MI identity resolution. Google Click IDs are platform-specific identifiers that cannot be resolved to a unified identity without the SDK or additional first-party data linkage.

Who Owns the Identity Problem

Identity resolution is fundamentally a customer data problem, not a Salesforce product limitation. The key qualifying questions:

  1. Can you identify the same person across your paid ad clicks and your CRM?
  2. Have you deployed the Salesforce SDK on your web and mobile properties?
  3. How do you currently handle anonymous-to-known user stitching?
SE Guidance

The easiest identity scenarios are Salesforce-native data (CRM contacts, MCE email recipients). The hardest are paid media–only touchpoints with no CRM linkage. Help customers understand what their identity coverage looks like before promising MTA outcomes — the SDK can be positioned as a roadmap item if not yet deployed.

SDK on the Customer Roadmap

For any user-level data use case (MTA, personalisation, identity-based segmentation), the SDK is required. If a customer doesn't have it deployed, it can be added to their implementation roadmap. It is not a blocker for starting with MI — but it is a dependency for full MTA capability.

Blockers vs. Dependencies

A blocker stops MI from launching. A dependency limits the depth of what MI can do — but doesn't prevent starting.

Hard Blockers
  • No willingness to sign Data Cloud — MI is built on it and cannot be separated
  • No data accessible from paid channels (locked APIs, no export)
  • Under 6 months of conversion history
  • No agreed definition of a conversion event
  • No internal owner or exec sponsor — MI requires someone to drive the implementation
Dependencies (limits scope, not launch)
  • No SDK → MTA not available; channel-level attribution still works
  • Messy naming → Harmonization phase required before Patterns unlock full value
  • No first-party data strategy → limits identity resolution depth
  • Short history → MMM runs but with lower confidence; grows over time

Demo Tips & Discovery Guidance

Getting the most out of MI demos requires upfront discovery. The more you understand the customer's data and naming conventions before the demo, the more relevant and compelling the story.

Discovery Questions

💡
Ask a customer to share their naming conventions, taxonomies, and UTM parameters before the demo. Harmonization and Patterns can then be shown with their actual data structure — infinitely more impactful than generic examples.
Business & Measurement Maturity
  • What does marketing ROI mean to your organisation today — revenue, pipeline, MQLs?
  • How do you currently measure cross-channel performance? One dashboard, multiple tools, or spreadsheets?
  • Who owns the marketing measurement conversation — marketing ops, analytics, finance?
  • What decisions do you make with marketing data today, and what decisions are you unable to make?
  • Have you run MMM before? Who owned it, and how long did it take to get a usable output?
  • How often does the CMO ask "which channel is actually driving results?" — and what's the current answer?
Data Sources & Stack
  • Which paid channels are you running today? (Google, Meta, LinkedIn, programmatic, CTV, affiliate…)
  • What's your primary owned channel — email, SMS, push? Is that in Marketing Cloud Engagement today?
  • Where does your conversion or revenue data live? CRM, data warehouse, commerce platform?
  • Do you have a data warehouse or lake (Snowflake, BigQuery, Databricks)? Is MI expected to sit on top of that or replace it?
  • What BI or reporting tools are your analysts using today? How much of that could MI absorb?
  • Are there any channels where the data is locked — no API access, no raw export?
Campaign Naming & Taxonomy
  • What does a typical campaign name look like? Can you share an example?
  • What metadata is encoded in your campaign names — brand, region, product, channel, tactic?
  • Is your naming convention documented and enforced, or does it vary by team and platform?
  • How consistent is UTM tagging across your paid channels? Do you have a taxonomy doc or UTM builder?
  • Who is responsible for campaign setup and tagging — a central team or individual channel owners?
  • Have you had situations where the same campaign had different names across platforms?
Identity & Technical Readiness
  • Can you identify the same user across your paid ads and your CRM today?
  • Do you have the Salesforce Interaction SDK (web + mobile) deployed on your properties?
  • How is your first-party data structured — do you have a consistent customer ID across systems?
  • What's your cookie and consent posture? Are you collecting consented first-party identifiers at scale?
  • Do you have Data Cloud today? Is it actively in use, or just provisioned?
  • Who would own the technical implementation — your internal data engineering team, a SI, or Salesforce PS?
Conversion & Attribution Goals
  • What do you define as a conversion — only final purchase/close, or mid-funnel events like form fill, demo request, free trial?
  • How long is your typical buyer journey? Days, weeks, months?
  • Are you currently using any attribution model — last click, first touch, linear? Who chose it?
  • How much historical conversion data do you have accessible? 1 year? 2+ years?
  • Do you have confidence in the accuracy of your current conversion tracking, or are there known gaps?
  • Is there a business event coming up — budget cycle, campaign planning — where better attribution data would directly change a decision?
